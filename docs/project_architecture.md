# Diffuri: архитектура проекта

Этот документ — обзор всего проекта целиком: от высокоуровневой структуры до ключевых алгоритмических решений. Для детального описания отдельных подсистем см. отдельные документы (например, `input_architecture.md` для слоя ввода).

## 1. Назначение проекта

**Diffuri** — это C++-библиотека и CLI-утилита для численного решения систем обыкновенных дифференциальных уравнений (ОДУ) **методом рядов Тейлора с адаптивным шагом и (опционально) адаптивным порядком**.

Ключевые особенности метода:
- **Экспоненциально высокая точность** на гладких системах (погрешность `O(h^{M+1})`, где `M` — порядок метода, обычно 20–60).
- **Адаптивный шаг**: шаг подбирается так, чтобы локальная погрешность была в заданных пределах `rtol`/`atol`.
- **Строгие априорные оценки** радиуса сходимости ряда — шаг гарантированно лежит внутри круга сходимости, а не подбирается эмпирически.
- **Работа с жёсткими и хаотическими системами** (Лоренц, Ван дер Поль) там, где классические Рунге-Кутты требуют экстремально мелкого шага.

Проект реализует идеи статьи:
> Л. К. Бабаджанянц, К. М. Брэгман. «Реализация метода рядов Тейлора с автоматическим выбором шага интегрирования», *Вычислительные методы и программирование*, т. 13, 2012, с. 497–510.

## 2. Математическая основа

### Метод рядов Тейлора

Для системы `x' = f(x)` решение в окрестности `t₀` представляется рядом:

```
x(t₀ + h) = x(t₀) + x'(t₀)·h + x''(t₀)·h²/2! + ... + x⁽ᵐ⁾(t₀)·hᵐ/m! + O(hᵐ⁺¹)
```

Коэффициенты `xₚ = x⁽ᵖ⁾(t₀)/p!` вычисляются **рекуррентно** по специальным формулам, которые для полиномиальных систем сводятся к двум видам:

1. **Линейная часть**: `x_{k,p+1} = (p+1)⁻¹ · Σₗ a[k][l] · x_{l,p}`
2. **Нелинейная (произведение)**: `x_{k,p+1} = Σₗ x_{p(k),l} · x_{q(k),p+1-l}`

где `x_k = x_{p(k)} · x_{q(k)}` — схема разложения нелинейных мономов.

### Ограничение метода

Метод требует, чтобы правая часть системы была **квадратичным полиномом** (степень ≤ 2) от неизвестных функций. Для произвольных систем применяется цепочка приведений — именно это и составляет большую часть логики проекта.

## 3. Высокоуровневая архитектура

Проект разбит на 12 модулей, сгруппированных в 4 уровня:

```
┌─────────────────────────────────────────────────────────────────┐
│  УРОВЕНЬ 1: ПРЕДСТАВЛЕНИЕ                                      │
│  core/expression  — AST (7 типов узлов, фабрики, запросы)       │
└─────────────────────────────────────────────────────────────────┘
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│  УРОВЕНЬ 2: ПРЕОБРАЗОВАНИЕ СИСТЕМЫ                             │
│  input          — парсинг текста → RawSystem                    │
│  normalize      — y^(n) = RHS (разрешение относительно ст. производной) │
│  order_reducer  — сведение к системе 1-го порядка              │
│  autonomize     — x' = f(x,t) → x' = f(x,t), t' = 1            │
│  simplify       — алгебраическое упрощение деревьев             │
│  polynomization — МДП: замена sin/exp/ln/... на v_i             │
│  quadratize     — приведение к квадратичному виду (deg ≤ 2)    │
└─────────────────────────────────────────────────────────────────┘
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│  УРОВЕНЬ 3: ИНТЕГРИРОВАНИЕ                                     │
│  solver/taylor_spec    — извлечение T, S, a из системы          │
│  solver/taylor_table   — рекуррентные коэффициенты Тейлора      │
│  solver/convergence    — априорные оценки (ρ, τ, u⁻¹, v⁻¹)     │
│  solver/error_control  — норма L² локальной погрешности         │
│  solver/step_control   — выбор шага h                           │
│  solver/order_control  — выбор порядка M                        │
│  solver/solver         — главный цикл Solve                     │
└─────────────────────────────────────────────────────────────────┘
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│  УРОВЕНЬ 4: ОРКЕСТРАЦИЯ И ВВОД/ВЫВОД                           │
│  pipeline/runner — связывает все этапы в цепочку                │
│  pipeline/trace  — фиксирует снимки системы на каждой стадии    │
│  output          — форматирование отчётов и решений             │
│  cli             — разбор аргументов командной строки           │
│  main.cpp        — точка входа                                   │
└─────────────────────────────────────────────────────────────────┘
```

**Принцип изоляции:** каждый модуль ничего не знает о модулях выше по стеку. `normalize` не знает про `polynomization`, `solver` не знает про `output`. Связи только однонаправленные.

## 4. Пайплайн обработки системы

Полный путь от текста до численного решения:

```
Текст (stdin)
    │
    ▼
[1] ParseSystem (input)        ──► RawSystem (сырая система)
    │
    ▼
[2] Validate (input)           ──► проверка t₀, порядков, имен
    │
    ▼
[3] NormalizeSystem            ──► каждое уравнение: y^(n) = RHS
    │
    ▼
[4] ReduceOrder                ──► система 1-го порядка
    │                               (x_1, x_2, ... вместо x', x'')
    ▼
[5] Autonomize                 ──► если есть t в RHS: t' = 1, t(t₀) = t₀
    │
    ▼
[6] Polynomize                 ──► МДП: sin(x) → v₁, v₁' = cos(x)·x'
    │
    ▼
[7] Quadratize                 ──► x³ → q₁, q₁' = 3x²·x'  (deg ≤ 2)
    │
    ▼
[8] BuildTaylorSpec            ──► извлечение T, S, a (один раз)
    │
    ▼
[9] Solve (главный цикл):
    │   ├─ TaylorTable(spec, x, M+K)    — коэффициенты Тейлора
    │   ├─ PickOrder                     — адаптация M (§2.1.6, §2.3)
    │   ├─ PickStep                      — адаптация h (§2.1.2–2.2)
    │   ├─ table.Evaluate(h, M)          — следующее состояние
    │   └─ пока t < t_end
    ▼
Solution (траектория + метаданные)
    │
    ▼
[10] Output                    ──► SolvedView, CSV, отчёт в файл
```

**PipelineTrace** сохраняет снимок `RawSystem` на стадиях 1, 2, 3, 4, 6, 8 (после Solve — тоже). Это позволяет в отчёте показать систему «как она есть» на каждом этапе и отдельно — «чистый» вид без вспомогательных переменных.

## 5. Модули: краткий обзор

### 5.1. `core/expression` — дерево выражений

**Файлы:** `src/core/expression.h`, `src/core/expression.cpp`

AST-представление математических выражений через `std::variant` из 7 типов:

| Узел | Назначение | Пример |
|------|------------|--------|
| `Number` | Литерал | `3.14`, `1e-3` |
| `Function` | Имя переменной | `x`, `y`, `t` |
| `Constant` | Константа из таблицы | `pi`, `g` |
| `Derivative` | `x'`, `x''`, `dy/dt` | `Derivative{"x", 2}` |
| `Unary` | Унарный минус | `-x` |
| `Binary` | `+`, `-`, `*`, `/`, `^` | `x + y` |
| `Call` | Вызов функции | `sin(x)`, `pow(x, 2)` |

Дочерние узлы хранятся через `std::unique_ptr<Expr>` — уникальное владение, дерево не шарится. Создание только через фабрики (`MakeNumber`, `MakeBinary`, `MakeCallArgs`, ...) — это обходит проблему некопируемости `unique_ptr` внутри `initializer_list`.

### 5.2. `input` — ввод и первичная валидация

**Файлы:** `src/input/parser.{h,cpp}`, `src/input/input.{h,cpp}`

- **Parser** (`parser.cpp`) — рекурсивный спуск, поддерживает три нотации производных: штрихи (`x'`), Лейбниц ASCII (`dy/dt`), Лейбниц Unicode (`d²y/dt²`).
- **Input** (`input.cpp`) — классифицирует строки (уравнение vs начальное условие), собирает `RawSystem`, выполняет семантическую валидацию (достаточность IC, согласованность `t₀`).

### 5.3. `normalize` — каноническая форма

**Файлы:** `src/normalize/normalize.{h,cpp}`

Разрешает каждое уравнение относительно старшей производной: `y^(n) = RHS`. Требует линейности по старшей производной (иначе `NormalizeError`).

### 5.4. `order_reducer` — понижение порядка

**Файлы:** `src/order_reducer/order_reducer.{h,cpp}`

Система `x'' = f(x)` превращается в систему 1-го порядка:
```
x  = x
x₁ = x'
x₁' = f(x)
```
Возвращает карту `{"x_1" → Derivative{"x", 1}}` для последующего переименования в `x'` при выводе.

### 5.5. `autonomize` — автономизация

**Файлы:** `src/autonomize/autonomize.{h,cpp}`

Если система неавтономна (`t` встречается в RHS), добавляется уравнение `t' = 1` с IC `t(t₀) = t₀`. Это необходимо для МДП, который работает только с автономными системами.

### 5.6. `simplify` — алгебраическое упрощение

**Файлы:** `src/simplify/simplify.{h,cpp}`

- Свёртка констант: `2 + 3 → 5`.
- Нейтральные элементы: `x + 0 → x`, `x * 1 → x`.
- Развёртывание `Unary::Neg` в `Mul(-1, x)`.
- Приведение подобных через каноническую форму (сортировка через `Compare`).
- `CollapseRepeatedAtomicFactors`: `x·x → x²`.
- `MergePowers`: `x²·x³ → x⁵`.

Идемпотентна: `Simplify(Simplify(e)) == Simplify(e)`.

### 5.7. `polynomization` — метод дополнительных переменных (МДП)

**Файлы:** `src/polynomization/polynomization.{h,cpp}`, `library.{h,cpp}`, `function_class.h`

Заменяет неполиномиальные подвыражения вспомогательными переменными:
```
x' = sin(x)
```
превращается в:
```
x'  = v₁
v₁' = cos(x) · x' = v₂ · x'
v₂' = -sin(x) · x' = -v₁ · x'
```

Поддерживаемые функции (через `FunctionLibrary`): `inv`, `ln`, `exp`, `sin`/`cos`, `sh`/`ch`. Произвольные функции вызывают `PolynomizeError` — это ограничение метода, а не реализации.

### 5.8. `quadratize` — квадратизация

**Файлы:** `src/quadratize/quadratize.{h,cpp}`

Приводит полиномиальную систему к квадратичной форме (степень ≤ 2). Для каждого монома `M` степени `d ≥ 3` строится цепочка:
```
M = x_j · M',  M' = x_j' · M'', ..., пока степень ≤ 2.
```
Производная каждой новой переменной квадратична (правило произведения). Алгоритм жадный, не минимальный (минимальная квадратизация NP-hard).

### 5.9. `solver` — численное интегрирование

**Файлы:** `src/solver/*.{h,cpp}` (7 модулей)

| Подмодуль | Назначение | Статья |
|-----------|-----------|--------|
| `taylor_spec` | Собирает мономы T, схему S, коэффициенты a в `TaylorSpec` | §1 |
| `taylor_table` | Вычисляет таблицу `x_{k,p}` по формулам (4)–(5) | §1.2 |
| `convergence` | Априорные оценки: `ρ(α)` (радиус сходимости), `τ` (безразмерный шаг), обратные функции `u⁻¹`, `v⁻¹` | §1.3, §2.1.1, §2.1.2 |
| `error_control` | Норма L² локальной погрешности `ε(h)` | §2.1.4 |
| `step_control` | Выбор шага `h`: `h = clamp(min(IterativeCorrection(max(prior, posterior)), 2·h_old), h_min, h_max)` | §2.1.2–2.2 |
| `order_control` | Выбор порядка `M`: на первом шаге `argmax V(p)`, далее по триггеру `|h/H| > m` | §2.1.5, §2.1.6, §2.3 |
| `solver` | Главный цикл `Solve`: от `t₀` до `t_end` с защитой от `inf`/`nan` | §2.4 |

**Алгоритм выбора шага (step_control):**
1. `prior_step = τ · ρ` — гарантированно внутри радиуса сходимости.
2. `posterior_step = h_old · (1/ε(h_old))^{1/(M+1)}` — эвристика.
3. `IterativeCorrection` — итеративно ищет границу `ε(h) = 1` от `max(prior, posterior)`.
4. Ограничение роста `≤ 2·h_old` — страховка от резких скачков.

### 5.10. `pipeline` — оркестрация

**Файлы:** `src/pipeline/runner.{h,cpp}`, `trace.{h,cpp}`

- **`runner.cpp`**: `RunPipeline(text, opts)` — прогоняет систему через все этапы 1–8.
- **`trace.cpp`**: `PipelineTrace` — хранит снимки `RawSystem` на каждой стадии и метаданные вспомогательных переменных (`{"x_1" → Derivative{"x",1}}` и т.п.).

### 5.11. `output` — форматирование

**Файлы:** `src/output/output.{h,cpp}`

- `SolvedView` — чистое представление финального решения: `x_1 → x'`, `v_1` скрывается.
- `FormatSolved` — человекочитаемый отчёт: `steps`, `order`, `t_final`, значения функций.
- `FormatReport` — полный отчёт со всеми стадиями пайплайна.
- `WriteReportToFile` — запись в файл.

### 5.12. `cli` и `main` — интерфейс

**Файлы:** `src/cli/cli.{h,cpp}`, `src/main.cpp`

- `ParseCliArgs` — разбирает аргументы: `--trajectory PATH`, `--help`, позиционные `t_end M h_init log_path`.
- `SaveTrajectory` — запись траектории в CSV (точность 17 знаков, round-trip для `double`).
- `main.cpp` — читает stdin до EOF, прогоняет пайплайн, печатает стадии, опционально пишет отчёт и CSV.

## 8. Ключевые архитектурные решения

### 8.1. Квадратизация вместо произвольных полиномов

Метод Тейлора в форме [Бабаджанянц, Большаков] эффективен только при степени RHS ≤ 2. Альтернатива — реализация формул для произвольных степеней — значительно усложнила бы `taylor_table`. Поэтому `Quadratize` — обязательный этап.

### 8.2. Snapshot-based trace

`PipelineTrace` хранит полные копии `RawSystem` на каждой стадии, а не дельты. Это дороже по памяти, но:
- упрощает реализацию;
- делает API стабильным (переход на reconstruction-based вариант не потребует правок клиентов);
- системы в типовых задачах небольшие (десятки уравнений).

### 8.3. Двухфазный выбор шага

Вместо одной формулы используется комбинация:
- **Априорная оценка** (`τ·ρ`) — гарантирует сходимость ряда (математическая гарантия).
- **Апостериорная оценка** — учитывает фактическую погрешность.
- **Итеративная коррекция** — доводит до границы `ε(h) = 1`.

Это даёт одновременно математическую корректность и практическую эффективность.

### 8.4. Строгая типизация ошибок

Каждый модуль имеет свой класс исключения (`ParseError`, `NormalizeError`, `OrderReducerError`, `AutonomizeError`, `PolynomizeError`, `QuadratizeError`, `SolverError`). Это позволяет в CLI по `dynamic_cast` определить, на каком именно этапе произошёл сбой, и напечатать осмысленное сообщение.

### 8.5. `unique_ptr` для дерева выражений

Использование `std::unique_ptr<Expr>` вместо `shared_ptr` даёт:
- уникальное владение (нет скрытых общих поддеревьев);
- нулевой overhead по памяти и времени;
- необходимость явно клонировать (`Clone`) при подстановках, что делает мутации осознанными.

Плата — фабрики `Make*` вместо `braced-init-list`.

## 9. Типовой сценарий использования

```bash
# 1. Запуск интерактивно:
./Diffuri 10.0 30 1e-3 report.log
# (вводим систему через stdin, Ctrl+D в конце)

# 2. С сохранением траектории:
./Diffuri --trajectory out.csv 10.0 30 1e-3 report.log

# 3. Из файла (через pipe):
cat system.txt | ./Diffuri 10.0 30 1e-3 report.log
```

**Результат:**
- stdout: состояние системы на каждой стадии + финальное решение;
- `report.log`: полный отчёт со снимками на всех стадиях (опционально с чистыми представлениями);
- `out.csv`: траектория исходных функций (без вспомогательных).

## 10. Расширяемость

### Добавить новую математическую функцию в МДП
1. Добавить `Expansion` в `FunctionLibrary::Lookup`.
2. Добавить числовое вычисление в `EvalAt` (в `polynomization.cpp`).

Парсер и все вышестоящие модули трогать не нужно.

### Добавить новый тип AST-узла (например, `Integral`)
1. Добавить альтернативу в `std::variant` (`expression.h`).
2. Обновить фабрики и запросы (`expression.cpp`).
3. Добавить правило в грамматику (`parser.cpp`).
4. Обновить обходы во всех модулях, которые работают с AST: `simplify`, `polynomization`, `quadratize`, `taylor_spec`.

### Заменить метод интегрирования
Заменить только модуль `solver` (все 7 подмодулей). Пайплайн преобразований остаётся прежним — он готовит систему в каноническом квадратичном виде, пригодном для любого метода, работающего с полиномиальными RHS.

**Итого:** Diffuri — это не просто «решатель ОДУ», а **конвейер трансформации системы**: из произвольного текста через цепочку нормализаций получается каноническая квадратичная система, для которой метод Тейлора работает с математически обоснованными оценками шага и порядка. Каждый этап пайплайна — отдельный модуль с чёткими границами ответственности, что делает код тестируемым и расширяемым.
