# Модуль `input`: архитектура и принципы работы

Данный документ описывает первый слой вычислительного конвейера (пайплайна) проекта Diffuri: приём системы обыкновенных дифференциальных уравнений (ОДУ) от пользователя, её синтаксический разбор и первичную семантическую проверку.

**Относится к файлам:**
- `src/core/expression.h` / `.cpp` — дерево выражений (AST);
- `src/input/parser.h` / `.cpp` — синтаксический разбор;
- `src/input/input.h` / `.cpp` — сборка и валидация системы.

> **Примечание о путях.** Модуль `expression` физически находится в `src/core/`, но семантически относится к слою ввода — он предоставляет базовые структуры данных (AST-узлы), на которых строятся все последующие слои. Поэтому в данном документе он рассматривается в контексте `input`.

## 1. Назначение модуля

Модуль реализует трансформацию неструктурированного текста в строго типизированное абстрактное синтаксическое дерево (АСТ) и структуру `RawSystem`.

```
[Текст пользователя] ──► input ──► [RawSystem] ──► (остальной пайплайн)
```

**Ключевой принцип:** модуль намеренно изолирован от математической логики. Он не вычисляет производные, не строит полиномы Тейлора и не решает уравнения. Его единственная задача — корректно интерпретировать ввод, проверить базовую семантическую согласованность данных и подготовить их для последующих этапов (нормализации, понижения порядка, автономизации, полиномизации, квадратизации и интегрирования).

## 2. Место в общем пайплайне

Слой `input` — первая стадия полного пайплайна Diffuri. После него следуют:

```
  ┌───────────────────┐
  │     input         │  ← ParseSystem, Validate (этот документ)
  │  parser           │
  │  expression       │
  └────────┬──────────┘
           ▼
  ┌───────────────────┐
  │    normalize      │  NormalizeSystem: y^(n) = RHS
  └────────┬──────────┘
           ▼
  ┌───────────────────┐
  │  order_reducer    │  ReduceOrder: приведение к системе 1-го порядка
  └────────┬──────────┘
           ▼
  ┌───────────────────┐
  │   autonomize      │  Autonomize: x' = f(x,t) → x' = f(x,t), t' = 1
  └────────┬──────────┘
           ▼
  ┌───────────────────┐
  │  polynomization   │  Polynomize: МДП — замена неполиномиальных
  │     (library)     │  подвыражений вспомогательными переменными
  └────────┬──────────┘
           ▼
  ┌───────────────────┐
  │    quadratize     │  Quadratize: сведение к квадратичной форме (deg ≤ 2)
  └────────┬──────────┘
           ▼
  ┌───────────────────┐
  │      solver       │  Solve: метод рядов Тейлора с адаптивным шагом
  │  (taylor_*,       │  и порядком
  │   convergence,    │
  │   step/order/     │
  │   error_control)  │
  └───────────────────┘
```

Модуль `input` передаёт структуру `RawSystem` дальше по цепочке и **не знает** о существовании последующих модулей.

## 3. Входные и выходные данные

### Входные данные

Текстовое представление системы ОДУ. Поддерживается ввод из строки, файла или стандартного потока (`stdin`).

Пример ввода:

```
# Система осциллятора
x'' + sin(x) = y' + t
y'           = x*y - 1
x(0)         = 1
x'(0)        = 0
y(0)         = 0
```

### Выходные данные

Структура `RawSystem`, содержащая «сырое» представление системы точно в том виде, в котором её задал пользователь:

```cpp
struct RawSystem {
    std::string                   independent_variable;  // По умолчанию "t"
    std::vector<std::string>      functions;             // {"x", "y"}
    std::vector<Equation>         equations;             // Деревья lhs и rhs
    std::vector<InitialCondition> initial_conditions;    // Структуры {func, order, t0, value}
};
```

**Важно:** на этом этапе система **не нормализована**. Уравнения не обязательно разрешены относительно старших производных, а производные могут присутствовать в обеих частях равенства. Приведение к каноническому виду выполняется на последующих этапах пайплайна.

## 4. Трёхуровневая архитектура

Модуль спроектирован по принципу строгой иерархии с однонаправленными зависимостями. Каждый вышестоящий слой использует нижестоящий, но нижестоящий ничего не знает о существовании вышестоящих.

```
                     ВЫСОКИЙ УРОВЕНЬ (Система целиком)
                             ▲
                             │ использует
             ┌───────────────┴───────────────┐
             │           input               │  ParseSystem, Validate
             └───────────────┬───────────────┘
                             │ использует
                             ▼
             ┌───────────────────────────────┐
             │           parser              │  ParseExpression, ParseEquation
             └───────────────┬───────────────┘
                             │ использует
                             ▼
             ┌───────────────────────────────┐
             │       expression (core/)      │  Expr, Make*, ToString
             └───────────────────────────────┘
                      НИЗКИЙ УРОВЕНЬ (Абстрактное дерево)
```

| Слой | Зона ответственности | Изолирован от (ничего не знает про) |
|------|----------------------|-------------------------------------|
| `expression` | Структура данных (АСТ), фабрики узлов, обход дерева | Текст, синтаксис, токены, уравнения, системы |
| `parser` | Синтаксический анализ одной строки, лексический разбор | Смысл системы, файлы, stdin, семантические противоречия |
| `input` | Сборка системы, классификация строк, семантическая валидация | Символы, токены, правила грамматики, реализация парсера |

## 5. Слой `expression`: структура дерева

### Концепция

Математическое выражение (например, `x + y * sin(t)`) представляется не как строка, а как рекурсивная структура данных — дерево.

```
       (+)
      /   \
    (x)   (*)
         /   \
       (y)  (sin)
              |
             (t)
```

### Типы узлов

Базовый тип `Expr` реализован через `std::variant`, объединяющий **семь** типов узлов. Дочерние узлы (в `Unary`, `Binary` и `Call`) хранятся через `std::unique_ptr` (`ExprPtr`) для обеспечения уникальности владения и поддержки рекурсии.

| Тип узла | Описание | Пример в тексте |
|----------|----------|-----------------|
| `Number` | Числовой литерал (целое, дробное, экспоненциальное) | `2`, `3.14`, `-1e-3` |
| `Function` | Символьное имя переменной или неизвестной функции | `x`, `y`, `alpha` |
| `Constant` | Именованная константа (из файла или `extra_constants`) | `pi`, `g` |
| `Derivative` | Производная функции по независимой переменной | `x'`, `y''` |
| `Unary` | Унарная операция (пока только `Neg`) | `-x` |
| `Binary` | Бинарная арифметическая операция (`+`, `-`, `*`, `/`, `^`) | `x + y`, `t^2` |
| `Call` | Вызов математической функции (имя не проверяется парсером) | `sin(t)`, `pow(x, 2)` |

### API слоя

- **Фабрики:** `MakeNumber`, `MakeFunction`, `MakeConstant`, `MakeDerivative`, `MakeUnary`, `MakeBinary`, `MakeCall`, `MakeCallArgs`.
- **Запросы (обход дерева):** `IsLeaf`, `HasDerivative`, `MaxDerivativeOrder`, `CollectFunctionNames`, `CollectDifferentiatedNames`, `CollectConstantNames`.
- **Сериализация:** `ToString` (форматирование чисел через `std::to_chars` для краткости).

### Правило создания узлов

Узлы создаются строго через фабрики, а не через `braced-init-list` (фигурные скобки), так как `std::initializer_list` требует копирования элементов, что несовместимо с `std::unique_ptr`.

```cpp
// ПРАВИЛЬНО:
auto e = MakeBinary(Binary::Op::Add, MakeFunction("x"), MakeNumber(2.0));

// Для вызовов с переменным числом аргументов:
auto s = MakeCallArgs("sin", MakeFunction("x"));

// НЕЛЬЗЯ (не скомпилируется из-за unique_ptr):
// auto e = Expr{ Binary{Op::Add, Expr{...}, Expr{...}} };
```

## 6. Слой `parser`: синтаксический анализ

### Назначение

Преобразует одну текстовую строку в соответствующую структуру (`ExprPtr`, `Equation` или `InitialCondition`).

### Конфигурация (`ParseOptions`)

Парсер настраивается через структуру `ParseOptions`, передаваемую из слоя `input`:

- `independent_variable`: имя независимой переменной (по умолчанию `"t"`). Критично для валидации нотации Лейбница (в `dy/dt` знаменатель обязан совпадать с этой переменной).
- `constants_file` и `extra_constants`: позволяют парсеру на лету отличать константы от неизвестных функций.
- `line_offset`: сдвиг номера строки для корректного формирования сообщений об ошибках при разборе многострочных текстов.

### Внутреннее устройство

- **Лексер (Tokenizer):** разбивает строку на токены (числа, имена, операторы, скобки). Распознаёт производные в трёх нотациях:
  - Штрихи: `x'`, `x''`
  - Лейбниц (ASCII): `dy/dt`, `d^2y/dt^2`
  - Лейбниц (Unicode): `d²y/dt²`

- **Парсер (Recursive Descent):** обходит токены методом рекурсивного спуска согласно грамматике с учётом приоритетов операций (степень `^` > унарные > умножение/деление > сложение/вычитание).

- **Обработка унарного минуса:** `-X` транслируется в `Unary{Op::Neg, X}`. Разворачивание в `Mul(-1, X)` при необходимости делает уже модуль `simplify` на более поздних этапах.

## 7. Слой `input`: сборка и валидация системы

### Алгоритм `ParseSystem`

1. **Построчное чтение:** игнорирует пустые строки и комментарии (`#`).
2. **Классификация строк:**
   - Эвристика: если левая часть до знака `=` соответствует паттерну `имя [штрихи] (число)` (например, `x''(0)`), строка классифицируется как начальное условие (`ParseInitialCondition`).
   - В противном случае строка разбирается как уравнение (`ParseEquation`).
3. **Сбор метаданных:** автоматически формирует список `functions`, извлекая имена функций, встречающихся под знаком производной (через `CollectDifferentiatedNames`, в порядке первого появления).
4. **Валидация:** вызов `Validate(sys)` для проверки семантической целостности.

### Семантическая валидация (`Validate`)

В отличие от синтаксических проверок парсера, `Validate` проверяет математическую логику системы:

- **Независимая переменная:** не должна быть пустой и не должна совпадать с именами неизвестных функций или констант.
- **Полнота функций:** каждое имя из списка `functions` должно реально встречаться под знаком производной в уравнениях.
- **Достаточность начальных условий:** для каждой функции количество заданных начальных условий должно быть не меньше её старшего порядка производной в системе (например, если есть `x''`, должны быть заданы как минимум `x(t₀)` и `x'(t₀)`).
- **Согласованность `t₀`:** все начальные условия должны быть заданы в одной и той же точке `t₀` (иначе нельзя однозначно начать интегрирование).

> **Примечание:** `Validate` намеренно **не проверяет** автономность системы, разрешимость относительно старших производных, линейность по старшим производным и полиномиальность правых частей — это задачи последующих модулей (`normalize`, `autonomize`, `polynomization`).

## 8. Сквозной пример обработки

Рассмотрим систему:

```
x' = -y
y' =  x
x(0) = 1
```

### Классификация

- `x' = -y` ➔ Уравнение.
- `y' =  x` ➔ Уравнение.
- `x(0) = 1` ➔ Начальное условие (паттерн `имя(число)`).

### Синтаксический разбор (AST)

- `x' = -y` ➔ `Equation { lhs: Derivative("x", 1), rhs: Unary(Neg, Function("y")) }`
- `y' =  x` ➔ `Equation { lhs: Derivative("y", 1), rhs: Function("x") }`
- `x(0) = 1` ➔ `InitialCondition { "x", order: 0, t0: 0.0, value: 1.0 }`

### Формирование `RawSystem`

- `functions` = `{"x", "y"}` (собрано из `Derivative` узлов в порядке появления).

### Валидация

- Старший порядок для `x` и `y` равен 1.
- Для `x` задано одно условие (`x(0)`). **Достаточно.**
- Для `y` задано ноль условий. **Ошибка:** `InputError` (не хватает начального условия для `y'`).

## 9. Границы ответственности

| Задача | Ответственный модуль |
|--------|---------------------|
| Лексический и синтаксический разбор текста | `input` (слой `parser`) |
| Проверка согласованности порядков и начальных условий | `input` (слой `input`) |
| Приведение к каноническому виду `y^(n) = RHS` | `normalize` |
| Приведение к системе 1-го порядка | `order_reducer` |
| Приведение к автономному виду (`t' = 1`) | `autonomize` |
| Полиномизация (МДП: замена неполиномиальных подвыражений) | `polynomization` |
| Сведение к квадратичной форме (степень ≤ 2) | `quadratize` |
| Построение коэффициентов Тейлора и интегрирование | `solver` |

## 10. Обработка ошибок

Модуль использует строгую типизацию исключений для разделения ошибок ввода и логики:

| Тип исключения | Источник | Описание |
|----------------|----------|----------|
| `ParseError` | `parser` | Синтаксическая ошибка: невозможно разобрать токен, нарушен баланс скобок, неверный формат числа. Содержит точные координаты (`line`, `column`) и контекст (`expected`, `found`). Методы `Line()`, `Column()`, `Expected()`, `Found()` — PascalCase. |
| `InputError` | `input` | Семантическая ошибка или ошибка I/O: система противоречива (не хватает начальных условий, конфликт имён, разные `t₀`) или не удалось открыть файл констант. |

> **Важно:** `ParseSystem` не «проглатывает» синтаксические ошибки. Если в тексте есть невалидная строка, выполнение прерывается с выбросом `ParseError`.

## 11. Потенциал расширяемости

Архитектура модуля спроектирована с учётом будущих модификаций:

- **Новые математические функции:** парсер распознаёт любое имя перед скобкой как `Call` (например, `bessel_j0(x)`), поэтому парсер менять не нужно. Однако на этапе полиномизации (`Polynomize`) поддержка ограничена реестром `FunctionLibrary` (текущее покрытие: `inv`, `ln`, `exp`, `sin`/`cos`, `sh`/`ch`). Добавление новой функции потребует:
  1. Расширения `FunctionLibrary` (новое `Expansion` с уравнениями по аргументу `p`);
  2. Возможно, добавления числовой оценки в `EvalAt` (в `polynomization.cpp`).
  
  Произвольные функции (вне реестра) вызовут `PolynomizeError` — это не ограничение слоя `input`, а ограничение метода дополнительных переменных.

- **Новые типы узлов (например, `Integral`):** потребуется добавить тип в `std::variant` (`expression.h`), обновить методы обхода (`expression.cpp`) и добавить правило в грамматику (`parser.cpp`). Слой `input` изменений не потребует, но все вышестоящие модули (`simplify`, `polynomization` и т.д.) должны будут научиться обрабатывать новый тип.

- **Альтернативные форматы ввода (JSON, YAML):** достаточно реализовать новый адаптер, который будет заполнять структуру `RawSystem`. Весь последующий пайплайн (валидация, нормализация, интегрирование) продолжит работу без изменений.

- **Сбор всех ошибок сразу:** текущая логика прерывается на первой ошибке. Для реализации режима «показать все ошибки» достаточно:
  1. Ввести тип `ParseErrorList` (коллекция `ParseError`);
  2. Изменить логику `ParseSystem` на накопление исключений вместо их немедленного проброса;
  3. Бросать `ParseErrorList` по завершении разбора, если он не пуст.

## Приложение: математические обозначения проекта

Единые обозначения, используемые во всей кодовой базе (согласно `h_file_format.md`):

| Понятие | Как писать в коде / комментариях |
|---------|----------------------------------|
| Порядок метода | `M` (заглавная) |
| Шаг интегрирования | `h` |
| Число доп. членов для оценки остатка | `K` |
| Радиус сходимости | `ρ` (или `rho` в именах переменных) |
| Безразмерный шаг | `τ` (или `tau`) |
| Масштабирующие множители | `α` или `alpha` |

Греческие символы используются **только в комментариях и документации**. В именах переменных и полях структур — только латинские транслитерации.
